# Agent instructions

- Keep this repo as one Tampermonkey userscript, not a Chrome extension.
- Keep `userscript/katana-helpers.dev.user.js` generated by `tools/build-release.js`; do not hand-edit it. Treat it as a stable Tampermonkey bootstrap whose job is only to load `http://127.0.0.1:5174/katana-helpers.dev-runtime.js`.
- Put changeable dev-loader behavior in `tools/dev-runtime.js`, not in the installed Tampermonkey userscript. This lets agents validate loader fixes by restarting the local server instead of requiring Tampermonkey edits.
- Update the `sourceFiles` list in `tools/build-release.js` when adding, removing, or reordering source modules. This list controls both the release concatenation order and the dev loader manifest.
- Run `node tools/build-release.js` after source-module, metadata, UI, or behavior changes so `dist/katana-helpers.user.js`, `userscript/katana-helpers.release.user.js`, and `userscript/katana-helpers.dev.user.js` stay aligned.
- For local Tampermonkey testing or validation, prefer checking `http://127.0.0.1:5174/katana-helpers.dev-status.json` before restarting the dev server. The dev server reads the runtime, bundle, and status data from disk on request, so ordinary source, UI, selector, settings, and feature changes usually need `node tools/build-release.js` plus a page refresh, not a server restart.
- Restart the dev server with `powershell -NoProfile -ExecutionPolicy Bypass -File tools/restart-dev-server.ps1` only when the status or health endpoint is unreachable, the reported app/bootstrap/module/runtime status is stale or wrong after a build, `tools/dev-server.js`, `tools/dev-runtime.js`, startup scripts, or generated userscript metadata/bootstrap behavior changed, or the server is visibly serving errors/stale files.
- The installed dev userscript loads the server-side dev runtime, and that runtime loads one live bundle from the local dev server on each page load; avoid branch-based GitHub raw loaders, per-module `@require`, or sequential per-file fetches for dev.
- Only change dev userscript metadata (`@match`, `@grant`, `@connect`, update URLs, etc.) when unavoidable. If metadata changes, say clearly that the user must approve/install that one Tampermonkey update because agents cannot operate the extension editor directly.
- Bump the app/release version in `tools/build-release.js` and `src/core/constants.js` for every user-facing behavior or UI change.

Browser/tooling rules for agents:

- Do not use the Codex in-app browser for Tampermonkey validation. It does not run the user's installed Tampermonkey scripts, grants, or storage, so it cannot validate this app's real runtime behavior.
- For UI or user-facing behavior changes, validate in the user's existing Chrome tab by default unless the user explicitly says not to, the relevant site is unavailable, the dev userscript has not been installed yet, or another rule in this file forbids the validation path.
- Do not edit live Katana orders during validation. If a fake sales order named for Codex exists, use only that fake order for click/edit validation.
- Do not click destructive or reset controls unless the user explicitly asks for that specific action.
- After refreshing Katana, wait until `document.documentElement.dataset.katanaHelpersReadyVersion` and `document.documentElement.dataset.katanaHelpersReadyAt` are present before treating the helper as missing.
